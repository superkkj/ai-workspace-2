# AI와 개발하는 방법

## 목적과 작성 근거

원본 `superkkj/ai-workspace`에서 정리한 공통 개발 흐름을 이어받았습니다. 원본 문서는 2026-11-18에 조회한 「AI 개발 방식 정리」 대화의 핵심을 바탕으로 작성되었으며, 이 저장소에는 「절차적 프로그래밍 쉽게 이해하기」 세션의 작업 공간을 복제하여 적용했습니다. 이전 대화에서 제안한 내용과 현재 저장소에서 실제 완료한 설정은 구분하며, 완료 상태는 [STATUS.md](../../STATUS.md)에서 확인합니다.

대화에서 정한 판단 기준은 문서로 남기고, 다음 작업에서 필요한 문서를 다시 읽습니다. 기록을 쌓는 것과 AI 모델 자체를 재학습시키는 것은 다른 일입니다.

## 1. 목표와 완료 기준 정하기

기능이나 로직을 바꿀 때 다음 네 가지를 짧게 정합니다.

- 목표: 사용자가 어떤 일을 할 수 있게 만들 것인가?
- 완료 기준: 어떤 결과가 나오면 끝났다고 판단할 것인가?
- 영향 범위: 어떤 코드나 기존 동작에 영향을 주는가?
- 확인 방법: 어떤 검사와 사용 흐름으로 확인할 것인가?

작은 작업은 대화나 진행 기록에 몇 줄만 적어도 됩니다. 문서 오탈자 수정에 별도 계획서를 만들 필요는 없습니다.

## 2. 필요한 계획 검토하기

복잡하거나 영향이 큰 변경은 구현 전에 빠진 요구, 실패 상황, 기존 기능에 미치는 영향을 확인합니다. 계획의 설명이 그럴듯한지보다 완료 기준을 실제로 확인할 수 있는지가 중요합니다.

다른 AI의 검토를 받으면 요구 사항과 관련 코드·제약을 함께 전달합니다. 별도 검토 도구가 없으면 현재 도구에서 확인할 수 있는 범위를 점검하고 그 한계를 기록합니다.

## 3. 작은 단위로 구현하기

- 기존 지침, 코드 구조와 사용자의 작업 내용을 먼저 확인합니다.
- 한 번에 확인할 수 있는 범위로 나누어 변경합니다.
- 오류가 있으면 증상, 재현 조건, 근거를 확인한 뒤 원인을 좁힙니다.
- 같은 오류가 반복되면 수정뿐 아니라 놓친 검사나 작업 조건도 확인합니다.

다른 프로젝트에 이 문서들을 적용할 때는 기존 지침과 검사 체계를 먼저 읽고 필요한 부분만 병합합니다.

## 4. 필요한 검사와 실제 사용 확인하기

검사 명령은 프로젝트 설정, 스크립트, 기존 문서에서 찾아 확인합니다. 사용할 언어와 프로젝트가 정해지지 않았으므로 지금 이 저장소에는 확정된 빌드·테스트 명령이 없습니다.

| 변경 종류 | 확인할 내용 |
| --- | --- |
| 문서 수정 | 사실과 상태의 일치, 참조 파일과 링크, 빠진 설명 |
| 기능·로직 변경 | 완료 기준, 영향을 받는 동작, 관련 오류 조건 |
| 화면·사용 흐름 변경 | 관련 코드 검사와 실제 동작 확인. 실행 환경이 없으면 미실행 사유 기록 |
| 검사 자체의 신뢰성 문제 | 중요한 잘못된 동작을 검사에서 잡는지 확인하고 필요한 검사 보완 |

결과는 [CHECKS.md](CHECKS.md)에 **성공·실패·미실행**으로 나누어 기록합니다. 명령이 실행되지 않았거나 환경이 없었다면 검사 통과로 적지 않습니다. 빌드 성공만으로 사용 흐름 전체가 정상이라고 단정하지 않습니다.

[변이 테스트](https://stryker-mutator.io/docs/)는 코드에 작은 오류를 넣었을 때 기존 검사가 이를 잡는지 살피는 방법입니다. 중요한 로직에서 검사 누락이 의심되고 환경이 마련됐을 때 선택하며, 모든 작업의 필수 단계로 두지 않습니다. 원래 소스와 분리된 작업 공간 또는 이를 지원하는 도구를 사용하고 변경을 남기지 않습니다.

구체적인 남은 위험이나 필수 검사가 해결됐다면 불필요하게 검사 범위를 계속 넓히지 않습니다.

## Codex와 Claude Code의 역할 나누기

필요한 도구와 저장소 접근 권한이 있을 때 다음처럼 작업할 수 있습니다.

1. **Codex:** 완료 기준에 맞춰 구현하고 실제 검사 결과를 정리합니다.
2. **Claude Code:** 같은 변경 범위와 요구 사항을 읽고 독립적으로 검토합니다. 문제의 근거, 재현 조건, 남은 불확실성을 전달합니다.
3. **Codex:** 타당한 지적을 반영하고 영향을 받은 부분을 다시 확인합니다.

역할은 필요에 따라 바꿀 수 있습니다. 한 도구만으로 진행해도 되며, 이 문서만으로 도구 사이에 자동 전달이나 실행이 설정되지는 않습니다. 같은 파일을 동시에 수정한다면 작업 범위를 분리하고 최종 변경을 합칠 때 충돌을 확인합니다.

### 검토를 맡길 때 전달할 내용

- 작업 목표와 완료 기준
- 검토 대상 커밋·변경 범위 또는 변경 파일
- 기존 동작 중 유지해야 하는 조건
- 실행한 검사와 결과, 실행하지 못한 항목
- 특히 확인이 필요한 부분

검토 결과는 실제 문제와 근거를 중심으로 전달합니다. 취향에 따른 제안과 동작 오류를 구분합니다.

## 지침 파일 연결과 확인

공통 규칙의 원본은 저장소 루트의 `AGENTS.md`입니다. Codex의 지침 탐색 방식과 Claude Code의 가져오기 문법은 아래 공식 문서를 확인했습니다.

- Codex는 작업 경로에 적용되는 `AGENTS.md` 계열 파일을 읽습니다. 전역·프로젝트·하위 경로의 기존 지침도 적용될 수 있으므로 함께 확인합니다.
- 이 저장소의 `CLAUDE.md`는 같은 폴더의 `AGENTS.md`를 `@AGENTS.md`로 가져옵니다. Claude용 검토 지침만 짧게 추가했습니다.
- 최신 Claude Code에는 조건에 따라 `AGENTS.md`를 직접 읽는 기능도 있습니다. 이 저장소는 버전과 설정이 아직 확인되지 않은 환경에서도 공통 규칙을 전달할 수 있도록 공식 가져오기 방식을 사용합니다.
- 사용자 PC에서 실제로 파일이 읽혔는지는 아직 확인하지 않았습니다. Claude Code를 사용할 때 `/context all`로 로딩된 파일을 확인할 수 있습니다. 사용 버전이 명령을 지원하지 않으면 해당 버전의 지침 확인 방법을 따릅니다.
- 다른 AI나 웹 대화에서는 저장소 접근 여부를 확인하고 시작 요청문으로 필요한 파일을 읽도록 요청합니다.

## 자동화는 실제 명령을 확인한 뒤 추가하기

자동 훅, GitHub Actions, self-hosted runner는 반복할 검사와 실행 환경이 정해졌을 때 추가합니다. 현재 저장소에는 관련 설정이 없습니다. 사용자의 PC에서 명령을 실행하는 연결도 완료되지 않았습니다.

저장된 기록은 다음 작업의 참고 자료입니다. 모든 대화를 자동 저장하거나 도구 간 기억을 자동 동기화하는 설정은 별도로 필요합니다.
